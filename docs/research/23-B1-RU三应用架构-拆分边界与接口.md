# B1-RU 三应用架构：拆分、边界与接口

> 时间：2026-10-24 ｜ 性质：委托方裁定应用拆分后的架构定义，承接并精化 [22号](22-CDD3数据平台复用边界与集成方案.md)
> **增补（同日，形态终局）**：产品形态已裁定为 **SKU-B 私有化部署**（见 [24号](24-产品形态决策记录-SKU-B私有化部署与数据订阅.md)）——交付结构=**一个单体应用**（两前端+单体后端，内嵌目录模块）；本文的三应用定位为**代码模块结构**（单仓三模块），非交付件数；数据管理平台=开发商内部总仓，不交付。§六.3 部署形态已裁定，"建议 SaaS"作废。
> 委托方裁定（本文前提）：产品拆分为三个应用——**① 配件商城客户端**（终端客户查询与采购）／**② 配件商城管理端**（商城后台运营）／**③ 数据管理平台**（纯数据应用：所售配件的类目属性与适配关系管理）
> 证据分级：✅ 源码/原文核实 ｜ 🟡 建议/推断 ｜ ❓ 待委托方拍板

## 一、三应用职责边界

| | ① 商城客户端 | ② 商城管理端 | ③ 数据管理平台 |
|---|---|---|---|
| 用户 | 俄语买家（修理厂/汽配店/车主） | 运营方员工（中文） | 运营方数据人员（+系统内部调用） |
| 职责 | 按车找件、OE/货号检索、限时价商品展示（30天有效）、购物车/下单/在线支付（SBP/卡/对公）、订单跟踪、企业/个人注册 | 商品管理（目录件→可售 SKU：价格/库存/限时价/图片/俄语文案）、订单履约（发货/物流单）、客户与分级、赋码执行（N2）、记账对账、报表 | 类目与属性、车型库、配件主数据（OE/交叉号）、**适配关系（fitment）**、数据导入与质量、数据包接收与版本管理、向①②提供目录查询服务 |
| 明确不做 | 不写目录数据、不做后台管理 | **不维护类目/适配**（那是③的领地） | 不碰交易/价格/库存/用户 |
| 代码来源 | **新建**（俄语商城前台，19号 M1 最大新建项） | **底座与库存账复用，电商业务层大部分新建**（复用度约 20–35%，勘误见§七） | **派生自 CDD3 `data_platform`**（22号：目录域 ~3,400 行 + 治理/导入 + sync 子系统） |

**架构思想与 15 号一脉相承**：15 号定义"一套系统、两个面向"（面向买家/面向商家）——现在精确化为：①②是同一**商城业务域**的两个面向，③是独立的**数据域**。交易域与数据域分离，正是"数据在工厂加工、在门店消费"（22号总原则）的应用化表达。

## 二、与 CDD3 的复用映射（三应用里只有一个半是新建）

```
B1-RU 三应用                CDD3 存量                        新建工作量
① 商城客户端        ←（无直接对应）                    ←  全新（俄语前台+购买流）
② 商城管理端        ←  底座框架+库存账/主数据（~20–35%）←  电商业务层大部分新建（勘误见§七）
③ 数据管理平台      ←  data_platform 派生              ←  精简拷贝+俄语字段+数据包接收
```

CDD3 的双域结构（`data_platform` vs `cdd_platform`）在**数据域与业务域分离**这一点上与本拆分同构；但 ② 对业务域的复用仅限底座与库存账——`cdd_platform` 的 sales/delivery/finance 实为 SaaS 公司自身的 CRM/交付项目/订阅收款（§七勘误），电商后台需按新建对待。

## 三、运行拓扑与数据流

**部署**：三应用同驻俄云同一私有网络（VPC）；①②调用③走**内网 API**（同域，延迟/可用性可控）——22号否决"实时 API"的理由是**跨境**调用，应用内网化后不再成立；跨境的只剩"总仓→③"这一条低频数据包通道。242-FZ：全部驻俄境内。

```
                 数据包（版本化，低频，跨境唯一通道）
CDD3 总仓（中国，数据工厂）──────────────────▶ ③ 数据管理平台（俄云）
   ▲  回流变更集（P1，审核后进总仓）                 │ 内网只读 API：按车找件/OE/交叉号/类目
   │                                              ▼
   │                              ① 商城客户端 ── 同一商城业务后端（交易/支付/
   └────────────────────────────── ② 商城管理端    记账/库存/客户/赋码 域）
        （②引用③的目录ID组商品；商品的价格/库存/订单都在业务后端，不在③）
```

| 数据流 | 通道 | 频率 |
|---|---|---|
| 总仓→③ 目录数据（车型/适配/交叉号/类目） | 版本化数据包（`models_sync` 子系统对准此用途） | 初始装载+月度/按需 |
| ①→③ 目录查询 | 内网 REST（只读，`serializers_fitment` 查询面） | 高频（买家找件） |
| ②→③ 选件/引用 | 内网 REST（只读"选件器"） | 中频（组商品） |
| ③→总仓 回流 | 变更集上传（P1，合同条款见22号§七.3） | 低频 |
| ② 内部 | 价格/库存/订单/收单/赋码全部在商城业务后端（20号裁定：记账+收付款在系统、结汇归运营方） | — |

**单一事实源**：目录主数据——实例内看③，全网看总仓；价格/库存/订单——商城业务后端。两域只靠"目录 ID 引用"衔接，无双向写。

## 四、应用间接口契约（"接口互通"的落地清单）

| # | 接口 | 方法面 | 关键约定 |
|---|---|---|---|
| I1 | 目录查询 API（③→①/②） | 按车找件（车型→品类→件列表）、OE/货号检索、交叉号展开、类目树浏览 | 只读；结果可缓存（数据随包更新，缓存失效以包版本号为键）；返回中带俄语字段与限时价关联键 |
| I2 | 选件器（③→②） | 商品编辑时按车/OE 选目录件，回填目录 ID | 只读；②不提供数据编辑 UI（数据编辑在③自带界面，CDD3 已有 admin/导入工具） |
| I3 | 数据包接收（总仓→③） | 包上传→校验→幂等导入→版本登记 | 契约先行（字段/schema 版本/授权范围标记，22号§四.4） |
| I4 | 回流上传（③→总仓，P1） | 商家补录的适配/交叉号变更集 | 待审核状态机；通过前只在本地实例生效 |
| — | ①与②之间 | **无跨应用接口** | 同属商城业务后端域，仅前端分离（各自 i18n：①俄语、②中文） |

## 五、对 22 号结论的精化（勘误说明）

| 22号原文 | 精化后（本文） |
|---|---|
| "拷贝目录域到商城内嵌只读镜像" | **③作为独立应用派生自 CDD3**——运营方需要在③里自主管理数据（加类目、补适配、收数据包），纯只读镜像不够用；且③部署在同域，内网 API 的性能异议消失 |
| "API 互通降级为低频通道" | 适用于**跨境**（总仓↔③）；**同域内网**①②↔③ 用 API 是正确形态 |
| 工厂/门店二分 | 变为三层：**总仓（中国）→ ③实例内数据域 → ①②门店交易域**；22号职责边界表仍有效，工厂职责由总仓与③分担 |
| 受控拷贝纪律（§四） | **全部继承**，适用于③的派生：拷贝清单化、只加不改、schema 版本对齐、数据包契约先行、回流协议 |

## 六、留给委托方的决策点

1. **代码库拓扑**：B1-RU 单仓三应用（`apps/storefront` + `apps/admin` + `apps/data_platform[派生]`，monorepo 延续 CDD3 治理习惯，🟡建议）vs 三仓分立？
2. **③的数据编辑权限**：运营方在③里可否自建类目/车型（总仓数据包之外）？——🟡建议允许（本地即时生效），重要变更走回流进总仓；需在合同中写清数据归属（22号§七.3）；
3. **部署形态**（22号§七.1 遗留）：~~俄云单实例 SaaS 多租户 vs 每客户私有化~~ **已裁定：私有化部署（SKU-B，见24号）**；
4. **限时价的归属确认**：30 天限时价是**商品属性**（②管理），不是目录属性（③）——已按此边界设计，请确认无异议。

## 七、勘误：② 的复用判断（2026-10-24，委托方质询后源码核实）

**原判断**（本文初版）："② 商城管理端 ← cdd_platform + store_services，大量复用（09号：国内门店场景完整度 85%）"。
**勘误**：该判断错误，两层失误：

1. **口径偷换**：09号的"85% 完整度"限定于"**国内门店 SaaS 场景**"（CDD3 对自身目标场景的完成度），被误用为"对 B1-RU 管理端场景的**复用度**"——属 04号批判过的口径偷换类错误；
2. **按名望义，未下钻模型层**。源码复核证实：
   - `cdd_platform/sales` = **CRM**（Lead/商机跟进），非商城订单；
   - `cdd_platform/delivery` = **软件交付项目管理**（业务调研→配置→培训→验收），非物流履约；
   - `cdd_platform/finance` = 平台收支 + **SaaS 订阅收款**，非商城收单对账；
   - `cdd_platform/invoice` = 门店级通用发票（唯一可参考）；
   - `store_services` = **连锁门店经营**（chain_hq/chain_store/workshop/garage/procurement/hr/marketing），是线下门店/车间的进销存与运营，非电商后台。

**修正后的复用地图（②）**：

| 层 | 内容 | 判定 |
|---|---|---|
| 底座框架 | schema 多租户、RBAC、Celery、文件存储、通知、报表框架、middleware/logging | ✅ 可复用 |
| 域模型 | warehouse 库存账（出入库记账）+ fitment_service 库存↔适配联动模式、master_data 主数据、invoice/finance（账期/对账 P1 参考） | ✅ 模型与账务逻辑可复用，**业务流程不通用** |
| 电商业务层 | 商品上架（目录件→可售SKU/俄语文案/图片）、订单生命周期（购物车→在线支付→发货→CDEK 面单轨迹）、收单对账、**限时价引擎**、赋码执行（N2）、客户分级、电商报表 | ❌ 全部新建 |
| 语言 | 整层俄语化 | ❌ 新建 |

**量化修正**：② 复用度约 **20–35%**（底座+域模型）。B1-RU v1 工作量口径随之修正：**①全新 + ②大部分新建 + ③派生**——这是一个正常规模的新开发项目，不是"裁剪 CDD3"。对 [20号](20-俄语区中国件直购商城可行性方案.md)§二.5"系统成本低（CDD3 复用）"的读法同步修正：成本优势集中在 ③（源码级核实）与底座，①②为正常新建投入；P3 路线与闸门纪律不受影响，受影响的是排期与定价的保守度。

**不变的结论**：三应用拆分本身（委托方裁定）不受影响，反而更必要——业务层不复用时，清晰的应用边界正是控制复杂度的手段；③ 派生的判断不受影响（依据为 data_platform 模型级核实，非模块名）。

**教训**：引用 CDD3 资产前必须下钻到模型/服务层核实；模块名不得望文生义；"场景完成度"≠"跨场景复用度"。
