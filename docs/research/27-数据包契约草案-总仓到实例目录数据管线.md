## 一、契约管辖范围

**管**（本文定义）：
1. **下行**：总仓（CDD3 `data_platform` 原身，中国侧）→ 实例（客户俄云单体应用内的 catalog 域）的**目录数据包**——I3 接口的全部约定；
2. **上行**：实例 → 总仓的**回流变更集**——I4 接口（P1 自动上传，契约与下行对称）。

**不管**（另行定义，不在本契约）：
- 实例内 ①② ↔ catalog 的内网查询接口（I1 目录查询 / I2 选件器，23号§四）；
- 商家商品数据（B 类：价格/库存/图片/文案）——属 commerce 域，**永不入包**；
- 应用代码版本与升级（24号§六.1 升级纪律，与包解耦）。

**数据范围（✅ 22号§二，仅 A 类通用目录数据；实体清单经源码勘定，CDD3 答复后定稿）**：品牌、车系、车型及 **12 张配置维表**、类目与属性字典体系、配件 SPU（含 OE 号与 SPU 属性值）、SPU 互换（交叉号）、适配关系及 Qdb 限定字典、**多市场命名表 entity_names**（总仓新建，ADT-DP-007；market=ru 为首行数据，替代原 ru_names 单语种方案）、俄语术语。按**品类包**裁剪（=Category 子树 × market 白名单，R2.8 拍板；授权标记落包 manifest，Q5）。

**不入包清单（勘定后明确）**：SKU/PriceBreak/ProductAsset/PackageLevel（商业与商家层，commerce 域）；`models_oem`（OEM 授权台账 FP06——总仓治理资产）；`models_mapping`（跨源车型映射/租户授权——总仓采集与治理资产）；CategoryMapping（前后台类目映射，v1 商城直接用后台类目树 🟡）；EPC 图册（预留）；VIN 缓存（随 VIN 直查 P1 再议）；三电件（26号§五.3）；**proprietary_tier ∈ {oem_proprietary, third_party_paid} 的行未经授权台账核对不下发**（PriceBreak 的 17VIN 4S 价默认 third_party_paid，恒不入包）。

## 三、包类型与版本号

| 类型 | 代码 | 用途 | 触发 | 内容 |
|---|---|---|---|---|
| 初始全量包 | `INIT` | 首建交付物（计入首建费，按品类包计价，G-02：500–2,000 行全链路） | 项目部署时一次 | 全量实体 + 类目框架 |
| 增量包 | `DELTA` | 订阅期常规供给（年费的实质内容，24号§五） | 月度/按需（23号§三） | upsert 变更集 + 墓碑删除 |
| 纠偏全量包 | `SNAP` | 消除增量累积漂移 | 🟡 季度 | 重建式全量（同 INIT 结构） |
| 回流变更集 | `FEED` | 实例补录/纠错回总仓（I4，P1） | 运营方导出/自动 | origin=local 的记录 + 对 hub 数据的纠错建议 |

**版本号规则（🟡）**：
- `pack_id = {SCOPE}-{SEQ}`：SCOPE=品类包代码（如 `BRAKE`），SEQ=该品类线内**全局单调递增整数**（0001 起，跨类型连续：INIT 0001 → DELTA 0002 → …）；同一 (客户实例, SCOPE) 的 SEQ 严格递增，禁止跳号；
- `schema_ver = MAJOR.MINOR`：目录 schema 的独立版本（MAJOR=不兼容变更，MINOR=新增字段/实体）；由总仓单方维护，随包声明；
- 人读日期放 manifest（`produced_at`），不参与排序逻辑。

│   ├── category_attribute_links.csv  叶引用（CategoryAttributeLink）

│   ├── spu_interchanges.csv    互换/交叉号（SPUInterchange）
│   ├── fitments.csv            适配关系（SPUFitment）
│   ├── fitment_footnotes.csv   适配脚注（FitmentFootnote）
│   ├── qualifier_dimensions.csv / qualifier_values.csv  Qdb 限定字典

- 命名：`B1RU-CAT-{SCOPE}-{TYPE}-{SEQ:4d}.tar.gz`；
- 载体 🟡：首期 **CSV**（UTF-8、逗号分隔、首行表头、`\N` 表空值）；理由：肉眼可查、Excel 可开、跨境通道无依赖；Parquet 等二进制格式待数据量到 MB 级再议（❓）；
- 体量预估（🟡）：首包 500–2,000 行 ≈ KB–低 MB 级；放量到十万行级仍在 10 MB 内，现有通道无压力。

## 五、数据契约：实体与字段（2026-10-25 勘定稿）

### 5.0 勘定结论总览

勘定对象：CDD3 `backend/data_platform` 根 `models.py` 及 `models_category` / `models_product` / `models_fitment` / `models_terminology` / `models_sync` / `models_mapping` / `models_oem`。**草案三处实体归位错误，已纠正**：

| 草案实体 | 草案猜的来源 | 勘定结果（实际模型 / db_table） | 差异说明 |
|---|---|---|---|
| cross_references | models_oem ❌ | **SPUInterchange**（models_product / data_platform_spu_interchange） | `models_oem` 实为 OEM **授权台账**（FP06：License/DataSource/Access），是总仓治理资产，不入包 |
| vehicle_series / vehicle_models | models_mapping ❌ | **VehicleSeries / VehicleModel**（根 models.py / data_platform_vehicle_series / vehicle_model） | `models_mapping` 实为跨源车型映射（SourceVehicleMap）+ 车辆类目标准映射 + 租户授权（TenantVehicleScope），均为总仓采集/治理资产，不入包 |
| ru_names | models_mapping ❌ | **无对应模型——总仓新建**（定稿拍板：落地泛化版 **entity_names**，非单语种表） | 现库只有 `*_en` 英文字段；CDD3 答复 R2.1 修正并升级为 entity_names（market+locale+name_type，GLOBAL 为市场无关默认，ru 是第一行数据）——多市场复用免费获得（ADT-DP-007） |
| part_spu | models_product ✅ | SPU（data_platform_spu） | OE 号在 SPU 层（`oe_number`），SPU 同一性=(brand, OE)；SKU/PriceBreak/ProductAsset 为商业层不入包 |
| fitments | models_fitment ✅ | SPUFitment（data_platform_spu_fitment）+ Qdb 字典 | 限定条件是独立字典体系（QualifierDimension/Value），须随包 |
| categories | models_category ✅ | Category + 属性词条体系 | 属性是"全局词条+叶引用"字典制（PRD-DP-CAT-004），比草案丰富 |
| terminology | models_terminology ✅ | IndustryTerm + TermAlias + OEMTermMapping | — |

**勘定新发现（草案未预见，已并入契约）**：
1. **品牌是前置实体**——草案漏了 Brand：车系/车型/SPU 全部挂在 Brand FK 上，品牌必须最先入包；
2. **车型挂 12 张配置维表**（年款/燃油/发动机/变速箱/驱动/制动/悬架/车身/货箱/转向/弹簧/GVWR，VCdb 式；CDD3 答复 R1.1 修正口径：12 张，其中 4 张现库 0 行随期 1 补齐——Q3），维表字典量小、全量下发；
3. **SPU↔类目是 N:M**（CategorySPU，含 is_primary 主类目约束）——SPU 挂类目需独立文件；
4. **全库主键为 UUID**——包引用天然全局唯一（见§5.2）；
5. **verified_status 三态已内建**（unverified/verified/disputed，SPUFitment 与 SPUSKUMapping 均有），且有 `verified_only()` 门店消费门控（未验证行不对门店可见）——正是"机器核验标签"的现成载体；
6. **proprietary_tier 授权维度挂在数据行上**（VehicleSeries/SPU/PriceBreak，取值 public/oem_proprietary/third_party_paid）——包构建时的授权过滤字段；
7. **冗余编码列是既有设计**（VehicleSeries.brand_code/brand_name、VehicleModel 的 series/brand 冗余列），随包下发、冲突以父表为准（PRD-DP-VHC-004 §8 R4 先例）。

### 5.2 通用列、主键与幂等键（源码核实后的修正）

- **主键全为 UUID**：包内引用天然全局唯一；实例补录（local）的新记录自带新 UUID，**无撞键风险**——草案设想的"hub/local ID 空间前缀分离"不需要，仅用 `origin` 列区分：`hub`｜`local`（FEED 包专用）；
- **质量分级改用源码既有 `verified_status` 三态**（unverified/verified/disputed），草案的两态 `src_status` 作废；源码 `verified_only()` 门控语义（未验证行不对门店可见）由实例前台沿用（disputed/unverified 行是否带标签展示 → 开放参数 12）；
- 所有实体带 `updated_at`（总仓侧时间）；行级幂等沿用种子包先例 `update_or_create`（键=各实体业务唯一键，见§5.3）。

### 5.3 唯一性约束预检清单（导入预检逐条核，违反即拒收）

| 实体 | 业务唯一键（源码约束名） |
|---|---|
| SPU | (brand_id, oe_number)，oe_number≠""（uniq_spu_brand_oe_number） |
| SPUInterchange | (source_spu, target_spu)（uniq_spu_interchange_pair） |
| CategorySPU | (category, spu) 唯一 + 每 SPU 至多一个 is_primary（部分唯一索引） |
| CategoryAttributeLink | (category, attribute)（uniq_category_attribute_link） |
| SPUAttributeValue | (spu, attribute)（uniq_spu_attribute_value） |
| 编码类 | brand_code / series_code / model_code / spu_code / category_code / attribute_code / term_code 等各自 unique |

**引用完整性**：包内引用必须闭合（fitment 引用的 spu_id/series_id/submodel_id、interchange 引用的 SPU 对、attribute_link 引用的词条等，要么在本包、要么已在实例库）；导入预检出"悬空引用"即整体拒收（见§七）。

### 5.4 与既有种子包机制的对齐（源码核实）

CDD3 已有一套"总仓出包→独立版灌入"的现成实现，**本契约在其之上演进而非另起炉灶**：

| 既有机制（源码） | 本契约的继承与扩展 |
|---|---|
| `export_standalone_seed.py`（总仓出包） | 复用导出骨架，扩展：品类包裁剪、增量diff、签名 |
| `import_seed_package.py`（灌入）：manifest.json 已有 `version` / `import_order`（依序灌入）/ `counts`（行数校验，不符=包损坏）；幂等=`update_or_create`（业务唯一键） | manifest 直接对齐（§4.2 已加 import_order/row_counts）；扩展：schema_ver/签名/checksums/墓碑/base_pack 依赖/实例ID 校验 |
| `SeedPackageExecution` 灌入快照（包版本+各表条数）+ `verify_seed` ≥ 基线校验（防升级丢种子、不误报客户增量） | 即§七.6 的 `catalog_pack_log` 版本登记——同构机制，B1-RU 侧沿用该表语义 |
| `SyncTask/SyncRecord/SyncConfig`（models_sync）：full/incremental/realtime × manual/scheduled/event_driven 的任务治理，含 conflict_resolution/data_validation JSON 配置位 | 定位为**总仓侧出包调度框架**（何时出包、出什么范围）；包格式与导入协议以本契约为准 |

## 六、版本兼容规则（schema 双轨落地）

1. **兼容窗口（🟡）**：实例应用须支持 `[当前 schema_ver − 1 个 MAJOR, 当前]` 内的所有包；总仓发不兼容包（MAJOR+1）前，须先发一个 MINOR 包预告弃用字段（`schema.json` 内 `deprecated` 标注），并给一个完整窗口周期的重叠期；
2. **导入时校验**：包 schema_ver 落在实例支持窗口内→放行；高于窗口→**拒收并提示升级应用**（这是唯一与代码升级联动的场景，manifest 的 `min_app_ver` 同时生效）；低于窗口→拒收（防陈旧包误装）；
3. **字段弃用**：deprecated 标注保留 ≥2 个 MINOR 周期后才可物理删除；删除前该字段在包中恒为空值；
4. **向上同步纪律（✅ 22号§四.3）**：CDD3 目录域模型变更→包 schema 变更，按"月度检查+重大变更即时"节奏；承接方式=变更 PR 打标 `b1ru-impact` + 月度对账会（R2.7 已承接）；
5. **前向兼容（定稿拍板，G6）**：导入协议实现 **manifest.schema_ver 协商 + 未知实体 skip+告警**模式（strict 显式开启时保留 fail-fast）——现导入器遇未知实体硬失败（CommandError），CDD3 期 1 改造；存量实例的升级先后序由 B1-RU 规划（28号§九④）。

## 七、导入协议（I3：上传→校验→幂等导入→版本登记）

```
①上传（管理端 F-21 界面，tar.gz）
②静态校验：签名验签 → checksums 逐文件核对 → manifest 结构完整
③兼容校验：schema_ver 窗口判断（§六）→ base_pack 依赖核对
   （DELTA：本地包日志中必须已登记 base_pack，缺失则要求先补装对应 SNAP）
④预检（dry-run）：行数 vs manifest.row_counts；主键冲突扫描；
   引用完整性扫描（悬空引用=拒收）；墓碑目标存在性
⑤事务导入：单事务内 upsert 全部实体 + 应用 deletes.json；
   任一步失败→整体回滚，库内零残留
⑥版本登记：写入 catalog_pack_log
   （pack_id/schema_ver/checksum/导入时间/各实体影响行数）
⑦导入后动作：实例 catalog_version ← pack_id（I1 查询缓存以其为键失效，
   23号 I1）；管理端出导入报告（中/俄）；FEED 无此步
```

**幂等细则（🟡）**：包级——pack_id 已在 catalog_pack_log 且 checksum 一致→跳过（no-op，出"已导入"提示）；pack_id 已登记但 checksum 不一致→**拒收并告警**（同号不同内容属总仓事故）；`SNAP` 重导 = 以 superseded_packs 重建，仍走全事务。**行级**——沿用种子包先例 `update_or_create`，幂等键=§5.3 的各实体业务唯一键（非仅主键）。

## 八、授权与范围标记（防串包）

1. manifest 带 `customer_instance` + `scope`（**授权范围标记落 manifest，Q5 拍板**：scope = market + Category 子树白名单）：导入时与实例自身 ID、已购范围比对，**不匹配即拒收**（✅ 承接 22号§四.4）；实例导入时授权范围落本地表，实例内部授权以 TenantVehicleScope 语义承接（包形态下实例≠SaaS 租户）；CDD3 前置动作=收敛三套租户标识为统一 UUID 软引用；
2. A 客户的包导入 B 客户实例：实例 ID 校验直接拦截；
3. 品类越界（scope 外实体出现在包内）：静态校验阶段拒收；
4. 订阅到期后的包：**不做远程锁死**（✅ 24号§六.3）——旧数据留在实例继续可用，新包不再下发（商业约束，非技术约束）。

## 十、回流变更集契约（I4，对称管线）

1. **形态**：与 DELTA 同构的 tar.gz（`B1RU-CAT-{SCOPE}-FEED-{SEQ}.tar.gz`），data/ 内全部记录 `origin=local`；另含 `corrections.json`：对 hub 数据的纠错建议（引用 hub 主键 + 建议值 + 理由）；
2. **状态机（✅ 23号 I4 待审核语义）**：实例内暂存（F-23）→ 导出 → 传递总仓 → **待审核** → 采纳（进主数据，随下版包全网分发）/ 驳回（回执通知实例）；通过前只在本地实例生效；
3. **冲突仲裁（🟡）**：回流内容与总仓已演进数据冲突时**总仓优先**，驳回并附差异说明；
4. **法律前提（✅ 24号§七.2）**：补录回流授权写入标准销售合同（客户授权开发商纳入总仓并随后续包分发）；
5. **对接**：v1 人工起步（G-04 回流审核流程人工化，26号§4.4），P1 变更集异步自动上传（可断连、可积攒，24号§六.4）。

## 十一、验收标准（G-01 关闭判据，对齐 26号§九.3/§九.6）

1. 总仓能生产 INIT/DELTA/FEED 三型测试包，签名与校验文件齐备；
2. 实例侧完成一轮"上传→校验→导入→登记"全流程演练（真实品类数据 ≥500 行）；
3. 负面用例全过：篡改包（验签失败）、schema 超窗（拒收+升级提示）、缺 base_pack（拒收）、悬空引用（拒收）、同 ID 异 checksum（拒收+告警）、未知实体（skip+告警 / strict 模式 fail-fast——G6）；
4. 幂等演练：同包连导两次，第二次 no-op，库内数据与日志一致；
5. 断网演练：实例断外网出向后完成包导入（本地上传）与找件查询；
6. FEED 演练：补录→导出→总仓审核→采纳→随下一 DELTA 下发回实例（闭环一周转）。
