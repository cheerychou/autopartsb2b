# 内部资产盘点：CDD3 与本项目的映射、差距与成本模型

> 时间：2026-10-24 ｜ 方法：实地盘点 `/Users/zhoudabo/应用开发/CDD3`（README/CLAUDE/CHANGELOG/PRD文档/模型代码/提交历史/测试规模）
> 性质：承接信息收集计划第一类（内部盘点）——本报告是研发成本测算的地基，也是对委托方三项判断的独立验证
> 证据纪律：全部结论附代码/文档/提交证据；推断单独标注 ⚠️

## 一、结论摘要

1. **资产真实性远超预期**：CDD3 不是"两个产品"，而是一个治理成熟的 monorepo SaaS 平台——**2,447 次提交（2026-04-08 至 2026-10-24 持续活跃）、后端 Python 111.7 万行（不含迁移）、前端 TS/TSX 63.9 万行、后端测试文件 1,084 个 + 前端 530 个、270 个数据库迁移**。文档治理（编号体系/PRD/经验教训册/完成声明须附 commit 证据）达到商业团队水准。
2. **与本项目的关系比委托方描述的更紧密**：数据平台已内建**商用车数据包产品化蓝图**（PRD-DP-VHC-005，2026-10-17 定稿——商用车数据已入库存：全库 2,345 个车系，其中轻型货车 1,340/重型 712/中型 162/客车 48。**［口径标注 2026-10-25：本断言基准为 2026-10-17 盘点时库，现已过时——CDD3 2026-10-25 cdd_dev 实测 passenger 车系 15,000（总 17,496/车型 99,660/SPU 823,901/适配 262,004，ZF 适配锚定带入），"乘用车骨架空白"不再成立；工作面重述为"俄市中国品牌覆盖度盘点与补齐"，见 [28a-CDD3答复](28a-CDD3答复.md) R2.5］**）+ **类目级数据授权机制已上线**（`TenantVehicleScope`）；**OEM 授权台账已建**（REF-DP-STD-005，定位"台账型"、可信数据空间为储备路线）。08 号报告研究的"目录数据空位"，**CDD3 数据平台本身就是那个载体**。
3. **"85% 完整度"需要分层理解**：对国内门店 SaaS 场景，85% 可信（框架成熟、当前工作重心已在数据填充：febi 制动件 48,876 行属性、ZF 81,594 SPU + 40,205 行适配、滤清器 23,242 行——最近两周的提交全是这个）；对**出海 B2B 场景**，估计 50~60%：多语言（前端 i18n 骨架已有、翻译未做）、多级 B2B 层级（法人公司-经销商）、索赔单流、海外云部署是主要缺口。
4. **成本模型改变决策结构**：AI 原生开发 + 单元工作组 + **约 10 万元/年**的研发成本口径若可持续，则研发成本从"决定性变量"降级为"背景变量"——**"3~5 套即可做"的判断自动成立，立项瓶颈完全转移到销售侧**。这与 05/07 号报告"销售通路是稀缺资源"的结论互相印证。

## 三、与福田DCMS 36项功能的差距分析

> 对照 `06号文档` §1.2 的功能清单。标注：✅ 有现成模块 / 🟡 有底座需改造 / ❌ 缺

| 福田DCMS 需求 | 现状 | 差距说明 |
|---|---|---|
| 配件订单：提报/审核/状态跟踪 | 🟡 | procurement 有采购申请状态机（门店视角）；需新建"经销商→法人公司"的上行订购门户与层级 |
| 配件订单：合同/回款/发票 | ❌ | 订单结算有（订单），但合同管理、发票管理无 |
| 配件库存：出入库 | ✅ | warehouse 模块 |
| 配件库存：对接属地第三方WMS | ❌ | 需新增集成层（已有 integration 目录骨架） |
| 配件主数据：产品/价格 | ✅ | data_platform SPU/OE/价格——**反而是可反向输出给车企的强项** |
| EPC 嵌套/电子图册 | ✅（反向） | `models_epc.py`/`views_epc.py`——CDD3 自己就是图册方，不是嵌套方 |
| 配件财务：开票 | ❌ | 需新建 |
| 服务索赔：记录/提报/审核/结算 | 🟡 | workshop 工单覆盖维修过程；"索赔单"流（对车企索赔）需新建——与"企业账期"同属 B2B 财务域 |
| 销售线索/CRM | 🟡 | marketing 模块 + 联友DMS对标功能清单可循 |
| 整车订单/库存/渠道/主数据/财务（12项，二期） | ❌ | 门店SaaS无整车业务——福田也放二期，不构成一期门槛 |
| 多语言（中英泰俄西德） | 🟡 | 前端 i18n 骨架在；六语种翻译与后端国际化需专项 |
| 海外公有云部署+数据脱敏中转 | ❌ | 部署架构单机 Docker Compose 起步，需海外云方案 |
| 属地财务记账系统对接 | ❌ | 按项目定制 |

**汇总**：一期强相关的配件域 14 项中——✅约4项、🟡约5项、❌约5项；加上多语言/部署两项横切。**"85%"对国内场景成立；对出海B2B一期场景的实际复用度约 50~60%**——但缺的部分（多语言、B2B门户、索赔流、部署）恰是 AI 原生开发模式下边际成本低的部分，且**不碰数据底座**。

## 四、"3~5套"经济学重算（基于 10万/年 成本口径）

| 变量 | 数值 | 来源 |
|---|---|---|
| 年研发成本 | ~10万元（算力+服务器，人员投入趋零） | 委托方口径（本轮采信，建议按季度复核算力账单验证） |
| B线单套定价 | 10~50万/套（出海汽配商，含实施） | 07号定价锚点推算 |
| C线单项目 | 200万+/个 | ✅ 鑫源招标门槛 |
| 盈亏平衡 | **B线 1 套即覆盖年研发；C线 1 个项目 = 20 倍年研发** | 推算 |

**结论**：在该成本结构下，"卖出3~5套"远超盈亏平衡线——委托方的立项标准实际上已经**自动满足**。真正的约束只剩两个：①销售通路（谁能把系统卖出去——05/07号报告的触达清单就是答案的骨架）；②**单维护者风险**：2,447 次提交中 94% 来自单一作者（zhoudabo），知识密度极高——建议在首个付费客户出现前完成关键文档化（docs 体系已具备此能力）。

## 五、风险与缺口清单（按优先级）

1. **商用车数据"门店口径"扩容**（014_truckhome 脊柱晋级工程）——B线/C线产品的数据前提，PRD 已定义但未排期；
2. **多语言专项**（六语种）——出海前置条件；
3. **B2B 多级层级**（法人公司-经销商门户）——C线项目的形态缺口；
4. **索赔单流**——C线投标的功能缺口（福田必查项）；
5. **海外部署合规**（境外云+脱敏中转，呼应俄罗斯242-FZ类要求）；
6. **单维护者风险**（94% 提交集中于一人）；
7. ⚠️ CHANGELOG 滞后（最新版本号停在 v0.3.0/2026-06，实际 10 月仍高频提交）——对外引用版本号时以 git 为准。

## 六、对既有研究结论的三点修正

1. **08号报告（目录数据来源）**：原报告假设目录载体需新建——修正为 **CDD3 数据平台就是载体**：SPU(OE)/fitment 引擎/GB44510 分类/ACES 对齐全部就位，08号"三条腿"策略（贸易商合作/厂商共建/EPC授权）直接作为 CDD3 的**数据供给策略**执行，REF-DP-STD-005 的授权台账正好承接 OEM 谈判成果。
2. **05号报告（协同资产假设）**："数字化门店×汽配商城数据标准打通"从假设升级为**已验证的存量能力**（warehouse.fitment_service 就是配件↔适配的联动点）；且门店端多品牌适配查询能力（fitment 引擎）是汽配云等竞品不具备的。
3. **09号成本口径**：此前所有报告隐含"研发是重投入"的假设作废。**立项决策树简化为一条：销售通路是否跑得通**——Gate 1（OEM/汽配商首个意向客户）之外的多数技术性验证都可以在拿到首单后再做。
