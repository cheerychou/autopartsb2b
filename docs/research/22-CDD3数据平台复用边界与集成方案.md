## 二、职责边界：数据工厂 vs 门店镜像

**总原则：数据在工厂加工、在门店消费；门店不加工数据，工厂不做交易。**

| | CDD3 data_platform（工厂，中国侧） | B1-RU 商城（门店，俄云） |
|---|---|---|
| 职责 | 数据源接入（08号三条腿：OEM EPC 授权/厂商共建/贸易商合作）、导入/清洗/治理（`cleansing_engine`/`quality_engine`）、车型库+配件 SPU+适配+交叉号+类目的**主数据管理**、俄语化与俄市命名映射加工、OEM 授权台账（REF-DP-STD-005）、跨客户资产沉淀、**数据包构建与分发** | 商品（=目录数据+价格+库存+运营信息）、交易/订单/**收单支付/记账对账**、客户分级（账期 P1）、赋码执行（N2）、限时价管理、俄语前台体验、**只读目录查询服务** |
| 数据角色 | 主数据的唯一写入源（Master） | 目录数据的只读镜像 + 商家自补数据的暂存（回流 P1） |
| 语言 | 中俄双语字段（俄语化加工在此完成） | 俄语展示（翻译成果随包下发，不在门店维护） |

**边界要点**：
1. 商城里没有"第二套车型库 schema"——商城的"商品"引用目录镜像的 ID，适配查询走镜像的查询服务；
2. 适配数据"从项目里长出来"（09号纪律）的**采集动作发生在两侧**：工厂侧专门整理 + 门店侧商家补录，但模型只有一个（CDD3 的），门店补录暂存后回流工厂审核入库（§七.3）；
3. 俄市命名映射（Tiggo 7 Pro Max 类）、俄语商品术语（`models_terminology`）都是**工厂资产**，随包分发。

## 三、集成方式对比与推荐

| 判据 | A. 实时 API 互通 | B. 全仓拷贝（fork 整个 data_platform） | **C. 精简拷贝 + 数据包分发（推荐）** |
|---|---|---|---|
| 部署/合规（242-FZ，俄云） | ❌ 商城找件是高频读，跨境调用（俄↔中）延迟与可用性不可控 | ✅ | ✅ 目录随商城驻俄境内，个人数据不出境 |
| 交付形态（单租户/私有化） | ❌ 客户实例被中心 API 绑架，离线不可用 | ✅ | ✅ 每实例自带只读目录，自主完整 |
| 查询性能 | ❌ 每次按车找件过一次跨境 API | ✅ 同库查询 | ✅ 同库查询 |
| 版本演进 | ✅ 单一代码库 | ❌ 整仓分叉，升级灾难（含门店/维修域等无关代码） | ◐ 仅目录域受控拷贝，分叉面最小（§四纪律） |
| 资产沉淀与学习效应 | ✅ 集中 | ❌ 各实例孤岛 | ✅ 门店补录回流工厂，资产仍归总仓 |
| 工作量 | 中（API 契约+鉴权） | 大（剥离无关域） | **中低：目录域模型仅 ~3,400 行** |

**推荐：C**。三个支撑事实：
1. **拷贝范围小**（✅ 本轮源码复核）：目录域 9 个模型文件合计 3,353 行——`models_epc`(128)/`models_fitment`(490)/`models_product`(933)/`models_category`(534)/`models_mapping`(224)/`models_oem`(356)/`models_sync`(292)/`models_vin_cache`(81)/`models_terminology`(315)，外加 `serializers_fitment` 查询面；
2. **分发机制有现成地基**（✅）：`models_sync.py` 已内建 SyncTask 子系统（全量/增量/实时 × 手动/定时/事件驱动、多数据源）——"工厂→实例"的数据分发不是从零发明，是把既有同步能力对准新用途；
3. **与 CDD3 自身方向同构**：CDD3 已有"商用车数据包产品化蓝图"（PRD-DP-VHC-005）与类目级数据授权（`TenantVehicleScope`）——按"数据包"对外供数本来就是它的演进路线，B1-RU 只是最先的一个消费方。

> API 互通不是被否定，而是**降级为低频通道**：工厂管理后台、回流上传、非紧急校验可用 API；买家找件路径上不出现跨境调用。

## 四、受控拷贝纪律（防止 fork 分叉失控）

1. **拷贝清单化**：记录来源 commit hash + 文件清单 + 剥离项，随 B1-RU 文档归档（沿用 CDD3 文档治理习惯）；
2. **只加不改**：B1-RU 不修改拷贝域的模型结构——需要新字段（如俄语名、赋码 GTIN）时开扩展表或 JSON 字段，保证与上游可合并；
3. **schema 版本对齐**：数据包带 schema 版本号；CDD3 目录域变更按"月度检查+重大变更即时"节奏同步到 B1-RU；
4. **数据包契约先行**：字段/类型/授权范围标记（TenantVehicleScope 思路）/幂等导入——先定契约再写分发代码；
5. **回流协议**（P1）：门店补录以"待审核变更集"上传工厂，审核后进主数据、随下个版本包下发全网——16号 VINQU"查询即采集"飞轮的实现位。

## 六、乘用车数据空白：这是工厂侧的数据工作，不是商城侧的代码工作

1. **现状**：CDD3 全库 2,345 车系均为商用车（09号）；B1-RU 首发需要中国品牌乘用车（奇瑞/哈弗/吉利/长安…）车型骨架+适配件——**空白在数据，不在引擎**（`models_fitment` 引擎对齐 ACES，与动力类型无关，✅ 09号）；
2. **来源**（08号三条腿+新工作面）：①俄市车型骨架+命名映射——公开车型目录可自建（中国品牌在俄约 40 个/数百车系，体量中等），这是**第一批数据包的候选内容**；②适配件——随首客经营品类共建（滤清/刹车/易损先行）；③OE/交叉号——OEM EPC 目录在俄侧可及（plentycar 先例，✅ 20号），授权谈判进工厂台账；
3. **首包定义建议**（🟡）：首客经营品类的全链路 500–2,000 行（车系→车型→适配→商品），先打通"工厂加工→数据包→门店按车找件"全链路，再谈放量；
4. **节奏纪律不变**：目录从第一单里长出来（09号），不为"建库"预投数据加工人力。

## 七、留给委托方的三个新决策点

1. **部署形态**：B1-RU = 俄云单实例 SaaS 多租户（CDD3 schema 级多租户正好复用，交付/运维成本最低）vs 每客户私有化部署（客户自主性强、单维护者运维负担×N）？——🟡 建议前者，242-FZ 下多租户同驻俄云即可合规；
2. **分发自动化程度**：首期手动出包/导入（够用、零开发），还是先建自动化管道？——🟡 建议手动起步，`models_sync` 的定时/增量能力后置启用；
3. **回流条款**：商家在门店补录的适配数据，合同上归谁？是否明确"回流总仓+全网下发"的权利？——❓ 涉及客户数据归属，需在标准销售合同里写清（这是 16号"查询即采集"飞轮的法律前提）。
